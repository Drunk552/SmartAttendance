# SmartAttendance 嵌入式工程化开发规范

## 1. 文档目的

本文档用于统一 SmartAttendance 智能离线人脸考勤终端的代码设计、开发、测试和评审标准。

本项目属于嵌入式 Linux/C++ 终端软件。工程化建设应围绕高内聚、低耦合、生命周期可控、资源受限、设备可替换、故障可恢复和行为可测试展开，不按照 Web 前后端项目进行拆分。

## 2. 规范等级

本文档使用以下规则等级：

- **必须**：强制要求，不满足时不得合并代码。
- **应该**：默认需要遵守，例外情况必须在代码评审中说明原因。
- **建议**：根据模块和目标硬件实际情况采用。

## 3. 总体工程原则

项目代码必须满足：

```text
高内聚
低耦合
单一职责
依赖方向明确
接口稳定
资源生命周期明确
错误可以追踪
行为可以测试
修改可以回退
```

禁止为了形式上的“架构先进”增加没有实际业务价值的抽象层。

### 3.1 C++17语言基线

项目所有自研 C++ 代码必须使用 C++17，CMake 必须设置：

```cmake
set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)
```

允许使用的典型 C++17 能力包括 `std::optional`、`std::variant`、`std::filesystem` 和 `std::string_view`。

禁止使用依赖 C++20 或 C++23 的语言和标准库能力，包括但不限于：

```text
std::expected
std::jthread
std::stop_token
std::span
std::format
std::ranges
```

需要类似能力时必须提供符合 C++17 的项目内实现或使用经过评审的轻量依赖。文档和代码中的 `Result<T, E>` 均指 `smart_attendance::Result<T, E>`，不得替换为 `std::expected`。

### 3.2 当前阶段技术栈基线

当前阶段只冻结会直接影响公共接口、构建行为和日常 PC 仿真的技术栈；硬件相关依赖等目标板确定后再冻结，避免把尚未验证的板卡假设写死。

| 技术项     | 当前基线           | 约束                                                                                |
| ---------- | ------------------ | ----------------------------------------------------------------------------------- |
| C++        | C++17              | 自研 C++ 代码统一使用 C++17                                                         |
| C          | C11                | 现有 LVGL 集成及自研 C 代码使用 C11                                                 |
| LVGL       | 9.4.0              | 以仓库内`libs/lvgl/lv_version.h` 为准，禁止无评审直接升级大版本或修改 API 兼容层  |
| CMake      | 最低 3.16          | 构建入口、预设和工具链配置必须兼容 CMake 3.16；实际 CI/开发机版本需在构建记录中保留 |
| PC 构建    | `simulator-full` | 使用 SDL2 完成日常 UI 仿真和完整流程验证                                            |
| 原型构建   | `rpi-zero2w`     | 用于树莓派 Zero 2 W 实体原型，具体驱动依赖待硬件联调确定                            |
| 低内存构建 | `target-lowmem`  | 用于后续 64/128MB 平台的能力裁剪和资源门禁                                          |

以下内容当前不冻结具体版本，只冻结“后续必须记录并验证”的要求：

- OpenCV 版本、模块集合、编译选项和人脸算法实现；
- 摄像头协议、V4L2/GStreamer 管线和像素格式；
- 目标板 Linux 内核、BSP、C 库、GPU/显示驱动和交叉编译器；
- SQLite、Freetype、SDL2、libxlsxwriter 等依赖在不同构建配置中的启用范围。

当目标硬件确定后，必须新增版本清单，记录实际版本、来源、许可证、编译选项、适用构建配置和校验值。未完成冻结前，不得把“当前 PC 可用版本”宣称为量产平台基线。

## 4. 模块职责规范

每个模块只能承担一种主要职责。

| 模块               | 允许职责                                         | 禁止职责                                 |
| ------------------ | ------------------------------------------------ | ---------------------------------------- |
| `app`            | 启动、退出、对象装配、线程生命周期和应用状态管理 | 计算考勤状态或作为全局Service Locator    |
| `core`           | 业务模型、纯业务规则                             | 调用 LVGL、SQLite、OpenCV                |
| `services`       | 业务流程编排                                     | 创建或操作页面控件                       |
| `biometric`      | 接收图像或模板，执行检测、注册、识别和模型管理   | 打开摄像头、拥有采集线程或直接写考勤记录 |
| `storage`        | Repository抽象、SQLite和文件持久化               | 判断迟到、旷工                           |
| `ui`             | LVGL显示、输入、页面导航和Presenter              | 直接执行SQL或管理后台线程                |
| `hal`            | 定义与板卡无关的硬件能力接口                     | 包含厂商SDK、设备节点和考勤规则          |
| `platform`       | 实现PC、Zero 2 W和低内存平台HAL接口              | 包含考勤业务规则或被Core反向依赖         |
| `infrastructure` | 日志、线程、事件、监控                           | 包含具体页面逻辑                         |

### 4.1 强制依赖方向

```text
LVGL Screen → Presenter → Services → Core
                              ↓
              Repository/Biometric/HAL抽象接口
                              ↑
                 SQLite/OpenCV/Platform具体实现

Application → 负责显式装配以上模块
```

必须禁止以下依赖：

```text
Core → LVGL
Core → SQLite
Core → OpenCV
Storage → UI
Biometric → UI
UI → SQL
驱动层 → 考勤业务
HAL接口 → Platform具体实现
Presenter → LVGL控件对象
```

培训要求中的 UI、业务、数据三层对应关系为：`ui` 属于 UI 层；`core/services/biometric/report` 属于业务层；`storage` 属于数据层。`app/hal/platform/infrastructure` 是嵌入式单体应用的装配和横切支撑模块，不属于Web后端分层。

### 4.2 认证模块边界

认证不得使用一个同时包含规则、数据库查询和密码库调用的 `auth_service` 文件。必须拆分为：

| 组件                      | 所在位置                    | 允许职责                                           |
| ------------------------- | --------------------------- | -------------------------------------------------- |
| `PasswordPolicy`        | `core/auth`               | 密码长度、格式、失败次数和锁定条件等纯规则         |
| `PermissionRule`        | `core/auth`               | 管理员、普通用户和敏感操作权限判断                 |
| `IPasswordHasher`       | `core/auth`               | 定义哈希生成和验证抽象，不依赖具体密码库           |
| `AuthenticationService` | `services`                | 查询用户、调用哈希验证、更新失败状态并生成认证结果 |
| `Pbkdf2PasswordHasher`  | `infrastructure/security` | 实现带随机盐的具体密码哈希和恒定时间验证           |

密码格式和权限规则必须可以脱离数据库、UI和硬件单元测试；认证用例测试必须使用假的 `IPasswordHasher` 和 Repository，不能依赖真实密码库或全局数据库。

## 5. 高内聚要求

### 5.1 一个类只负责一个核心概念

错误示例：

```cpp
class FaceManager {
public:
    void captureFrame();
    void recognizeFace();
    void calculateAttendance();
    void writeDatabase();
    void updateLvglLabel();
};
```

正确拆分：

```cpp
class CameraSource;
class FaceRecognizer;
class PunchService;
class AttendanceRepository;
class HomePresenter;
```

### 5.2 一个函数只完成一个明确操作

一个函数中不应该同时存在：

```text
读取UI输入
+ 查询数据库
+ 计算业务状态
+ 写文件
+ 更新页面
```

应该将不同职责拆成可以独立理解和测试的步骤。

### 5.3 代码规模评审阈值

- 普通函数建议不超过 50 行。
- 复杂函数超过 80 行必须评估拆分。
- 普通类建议不超过 500 行。
- 单个源文件超过 800 行必须说明原因并制定拆分计划。
- UI 页面可以适当放宽，但页面数据、业务调用和控件创建应该分离。
- 函数参数建议不超过 5 个；参数较多时应该使用配置结构体。

以上数值是代码评审阈值，不是机械限制。拆分后更难理解时，不应为了满足行数强行拆分。

## 6. 低耦合要求

### 6.1 依赖抽象接口

业务服务不能直接创建 SQLite、摄像头和厂商算法对象。

错误示例：

```cpp
PunchService::PunchService() {
    db_ = sqlite3_open("attendance.db");
}
```

正确示例：

```cpp
class PunchService {
public:
    PunchService(IAttendanceRepository& attendanceRepository,
                 IScheduleRepository& scheduleRepository,
                 IClock& clock);
};
```

抽象接口和具体实现必须通过名称与目录区分：

- `storage/repository/employee_repository.h` 声明 `IEmployeeRepository`。
- `storage/sqlite/sqlite_employee_repository.*` 实现 `SqliteEmployeeRepository`。
- `hal/camera.h` 声明 `ICamera`。
- `platform/raspberry_pi/v4l2_camera.cpp` 实现树莓派摄像头适配。
- `Application` 通过 `PlatformFactory` 和 `ApplicationServices` 完成显式装配。

### 6.2 禁止跨层访问

- LVGL页面必须通过对应 Presenter 发起业务命令并获取页面状态。
- Presenter 必须通过 Service 获取业务数据，不能直接访问 Repository。
- Service 必须通过 Repository 接口访问数据。
- Repository 不允许调用 UI。
- 人脸识别结果只能作为输入交给统一打卡服务。
- 硬件实现不能直接发布业务状态码。

### 6.3 限制全局变量和单例

必须逐步消除可修改的全局状态。

原则上禁止新增：

```cpp
static bool trained;
static sqlite3* db;
static std::vector<User> users;
```

只有同时满足以下条件时才允许使用文件内静态状态：

- 仅在单个源文件内部使用。
- 生命周期确实等同于进程。
- 已有明确的线程同步保护。
- 无法通过合理的对象所有权替代。

单例只允许用于真正的进程级基础设施，并且必须支持测试替换。

### 6.4 强类型事件模型

事件总线不能代替正常的函数调用和返回值。

适合事件总线的场景：

- 摄像头状态变化。
- 磁盘空间告警。
- 系统时间更新。
- 后台任务完成通知。

不适合事件总线的场景：

- 查询用户信息。
- 修改密码。
- 写入考勤。
- 返回必须立即确认的业务结果。

事件负载必须定义为具名结构体，结构体类型本身代表事件类型：

```cpp
struct TimeUpdated {
    std::string displayText;
};

struct DiskStateChanged {
    bool isFull;
    std::uint64_t freeBytes;
};
```

禁止继续使用：

```cpp
using EventCallback = std::function<void(void*)>;
void publish(EventType type, void* data);
```

事件总线公共接口必须保持编译期类型安全：

```cpp
template <typename Event>
SubscriptionHandle subscribe(
    std::function<void(const Event&)> handler);

template <typename Event>
void publish(const Event& event);
```

不需要额外设计通用 `Event<T>` 包装类。跨线程进入UI的事件必须组成有限的 C++17 `std::variant`，并进入有界队列：

```cpp
using UiEvent = std::variant<
    TimeUpdated,
    DiskStateChanged,
    RecognitionCompleted,
    CameraStateChanged>;
```

事件系统必须满足：

- `SubscriptionHandle` 只能移动，析构时自动退订。
- EventBus 通过构造函数注入，禁止实现为全局单例。
- 同步 `publish()` 的回调运行在发布线程，调用方必须清楚线程语义。
- 非UI线程禁止在事件回调中调用LVGL，只能向有界UI事件队列投递。
- 页面、Presenter或订阅者销毁前必须先销毁对应订阅句柄。
- 事件负载按值传递或使用生命周期明确的不可变值对象，禁止裸指针、局部变量地址和可修改共享引用。
- 摄像头帧不能作为事件负载复制，只允许发送帧序号、状态或固定缓冲索引。
- 事件处理器不得执行长时间数据库、文件、模型训练或设备IO操作。
- 事件总线内部如果使用类型擦除，不能把不安全的类型转换暴露到公共接口。
- 模板函数定义必须位于头文件或被头文件包含的实现文件中，禁止只在 `.cpp` 中声明模板导致目标平台链接失败。
- 发布时只能在锁内取得订阅者快照，执行回调前必须释放EventBus内部锁。
- 退订与发布并发发生时必须内存安全，并在接口文档中说明本次发布是否仍可能执行已取得快照的回调。
- EventBus或其共享状态必须比所有 `SubscriptionHandle` 生命周期更长。
- 单个事件处理器抛出的异常不得中断其他订阅者，必须在分发边界记录并转换为错误状态。
- UI事件队列满时必须为每种事件定义覆盖、丢弃、合并或阻塞策略，禁止静默丢弃考勤结果和设备故障。
- `std::function`和订阅容器可能产生动态分配，低内存配置必须测量订阅数量和发布路径分配行为。

### 6.5 Presenter边界

本项目采用适合 LVGL C 回调模型的轻量 Presenter，不采用依赖自动数据绑定的完整 MVVM。

Presenter允许持有：

- 页面加载、选中、筛选、分页和错误提示等UI无关状态。
- 业务Service的非拥有引用。
- 属于自身生命周期的 `SubscriptionHandle`。

Presenter禁止持有：

- `lv_obj_t*`及其他LVGL控件指针。
- SQLite连接、Repository具体实现和平台设备实现。
- 后台线程、摄像头帧缓冲和全局可变状态。

Presenter由页面或UI管理器创建，在页面销毁前释放。Presenter方法默认只能在UI线程调用；后台结果必须先进入UI事件队列。Presenter不得实现为单例，不得提供与现有 `UiController` 相同的全功能接口集合。Presenter对页面暴露的数据必须是领域值对象或UI DTO，禁止直接暴露 `db_storage.h` 中的数据库结构体。

现有 `UiController` 必须按以下方向拆分：

| 当前职责                       | 目标位置                    |
| ------------------------------ | --------------------------- |
| 员工、排班、导出和维护流程     | 对应Service                 |
| 页面选择、筛选、加载和提示状态 | 对应Presenter               |
| SQL和数据库结构体              | Repository与领域/UI DTO     |
| 摄像头采集和图像缓存           | Camera Worker与有界缓冲     |
| 时间、磁盘和摄像头后台线程     | `TaskManager`管理的Worker |
| 全局单例访问                   | 删除，由Application显式注入 |

### 6.6 Application对象与线程所有权

- `Application` 是唯一组合根，负责调用顺序，不承担具体业务。
- `ApplicationServices` 使用显式成员持有Repository、Service、算法和基础设施对象。
- 禁止在 `ApplicationServices` 中实现字符串、枚举或模板形式的通用 `getService()`，避免形成Service Locator。
- `ApplicationServices` 不创建和启动线程。
- `TaskManager` 只拥有Worker、停止标志、队列和线程，不创建业务Service。
- Worker通过构造函数接收所需Service或HAL接口引用，禁止运行时从单例查找依赖。
- 启动顺序必须是Service和HAL就绪后再启动Task；停止顺序必须是停止新输入、请求Task停止、join线程、最后销毁Service和存储资源。

## 7. 接口设计规范

### 7.1 接口必须表达失败原因

不建议：

```cpp
bool saveAttendance();
```

建议：

```cpp
enum class SaveAttendanceError {
    None,
    DatabaseUnavailable,
    StorageFull,
    InvalidUser,
    DuplicateRecord
};

Result<void, SaveAttendanceError> saveAttendance(
    const AttendanceRecord& record);
```

上述 `Result` 必须是 `core/common/result.h` 中定义的 `smart_attendance::Result<T, E>`，不是 C++23 的 `std::expected`。实现要求：

- 普通 `Result<T, E>` 可以使用 C++17 `std::variant<T, E>` 保存成功值或错误值。
- 必须为 `Result<void, E>` 提供明确特化，不能使用无效的 `std::variant<void, E>`。
- 必须提供可读的成功判断、取值和取错接口，禁止依赖异常区分分支。
- 取值前必须检查状态；错误取值行为应在接口中明确，不能静默返回默认值。
- 不得隐式把错误转换成成功，也不得用一个通用整数同时表达所有模块错误。

返回类型选择规则：

| 场景                         | 推荐类型                                     |
| ---------------------------- | -------------------------------------------- |
| 不会失败的纯计算             | 直接返回值                                   |
| 查询结果可能不存在但不是错误 | `std::optional<T>`                         |
| 可预期业务或设备失败         | `Result<T, ErrorEnum>`                     |
| 第三方库异常                 | 在模块边界捕获并转换为`Result`或明确错误码 |

### 7.2 禁止魔法数字

错误示例：

```cpp
if (status == 4) {
}
```

正确示例：

```cpp
if (status == AttendanceStatus::Absent) {
}
```

硬件寄存器值、GPIO 编号、状态码和超时时间也必须使用具名常量。

### 7.3 参数与所有权

- 只读对象使用 `const T&`。
- 可以为空的观察指针使用 `T*`，并在接口文档中说明。
- 独占所有权使用 `std::unique_ptr`。
- 只有确实需要共享所有权时才使用 `std::shared_ptr`。
- 禁止使用裸指针表达资源所有权。
- 禁止跨线程传递生命周期不明确的局部对象地址。

### 7.4 头文件要求

- 头文件必须能够独立编译。
- 禁止依赖其他头文件的间接包含。
- 优先使用前置声明减少依赖。
- 公共接口和内部实现应该分离。
- 禁止在头文件中使用 `using namespace`。
- 非模板实现不应放在头文件中。

## 8. 命名规范

| 对象             | 命名方式             | 示例                       |
| ---------------- | -------------------- | -------------------------- |
| 命名空间         | `snake_case`       | `smart_attendance`       |
| 类、枚举、结构体 | `PascalCase`       | `PunchService`           |
| C++函数          | `lowerCamelCase`   | `recordAttendance()`     |
| 局部变量         | `lowerCamelCase`   | `userId`                 |
| 私有成员         | 末尾下划线           | `state_`                 |
| 常量             | `kPascalCase`      | `kMaxQueueSize`          |
| 宏               | `UPPER_SNAKE_CASE` | `SMART_ATTENDANCE_DEBUG` |
| C接口            | `snake_case`       | `hal_keypad_init()`      |
| 文件名           | `snake_case`       | `punch_service.cpp`      |

补充要求：

- 禁止使用 `data1`、`tmp2`、`obj`、`mgr` 等含义不清的名称。
- 缩写必须是行业通用缩写，例如 `rtc`、`gpio`、`usb`。
- 数据库 ID 应统一使用 `userId`、`shiftId` 等名称，避免同一字段同时叫 `uid`、`id`、`user_id`。
- 中英文业务术语必须建立统一词汇表。
- 代码标识符使用英文，业务文档和注释可以使用中文。
- 所有源码统一使用 UTF-8 编码。

## 9. 注释规范

### 9.1 注释应该解释“为什么”

错误注释：

```cpp
// 设置状态为运行
state_ = ApplicationState::Running;
```

有价值的注释：

```cpp
// LVGL只能由UI线程访问，因此识别结果先进入UI事件队列。
uiEventQueue_.push(result);
```

注释应该说明：

- 为什么这样设计。
- 业务规则来源。
- 硬件或平台限制。
- 线程所有权。
- 资源生命周期。
- 异常处理和降级原因。
- 看起来奇怪但不能修改的兼容逻辑。

### 9.2 文件头注释

不要求在每个文件重复作者、日期和修改历史，Git 已负责版本记录。

公共模块可以使用：

```cpp
/**
 * @file punch_service.h
 * @brief 统一处理人脸、指纹、卡片和密码认证后的打卡流程。
 */
```

禁止在代码中长期维护容易过期的版本号、作者和手工修改历史。版本和修改记录应由 Git 标签及发布说明管理。

### 9.3 公共接口注释

公共接口应说明输入、输出、失败原因、线程、所有权和副作用。

```cpp
/**
 * @brief 根据认证结果生成一条考勤记录。
 *
 * @param userId 已通过身份认证的用户ID。
 * @param snapshot 打卡现场图像，可以为空。
 * @return 成功时返回考勤结果；失败时返回明确错误码。
 *
 * @thread 只能从打卡工作线程调用。
 * @note 数据库记录成功写入后才返回打卡成功。
 */
PunchResult punch(int userId, const ImageFrame& snapshot);
```

公共接口至少应该说明：

- 输入含义。
- 输出和失败原因。
- 是否允许空值。
- 调用线程。
- 参数所有权。
- 重要副作用。
- 超时或阻塞行为。

### 9.4 业务规则注释

复杂业务规则必须注明规则含义，必要时关联需求编号：

```cpp
// ATT-RULE-012：个人特殊排班优先于部门周排班和默认班次。
```

详细规则放在业务文档，代码注释只保留规则编号和关键约束。

### 9.5 TODO规范

禁止：

```cpp
// TODO: 以后再处理
```

统一格式：

```cpp
// TODO(owner/issue-id): 接入目标板RTC后替换POSIX模拟实现。
```

TODO 必须包含负责人或问题编号、未完成的具体内容，以及删除 TODO 所需条件。正式发布版本不允许包含未评估的高风险 TODO。

### 9.6 注释维护

修改代码时必须同步检查相邻注释。错误注释比没有注释更危险。代码评审发现注释与实现不一致时，必须在当前修改中修正。

## 10. 错误处理规范

- 正常业务失败使用 `Result`、错误码或明确枚举。
- 禁止用异常表达“用户不存在”“重复打卡”等正常情况。
- 第三方库异常必须在模块边界捕获。
- 异常不能跨越 C API、线程入口和硬件回调。
- 禁止没有处理逻辑的 `catch (...)`。
- 捕获异常后必须记录上下文或转换成明确错误。
- 禁止只打印错误后继续返回成功。
- UI 提示、日志错误和内部错误码必须相互对应。

错误日志至少包含：

```text
模块
操作
错误码
相关用户或记录标识
设备状态
底层错误信息
```

密码、人脸模板、指纹模板等敏感信息不得写入日志。

## 11. 线程和并发规范

- 禁止新增 `std::thread::detach()`。
- 所有线程必须有明确所有者。
- 所有线程必须支持停止和 `join()`。
- 线程必须由 `TaskManager` 或其拥有的 `Worker` 管理，禁止由Presenter、页面、Repository和普通Service直接创建长期线程。
- LVGL API 只能由 UI 线程调用。
- 摄像头线程不能直接写数据库或操作 UI。
- 识别线程只负责输出识别结果。
- 打卡工作线程负责调用统一 `PunchService`。
- 队列必须有明确容量上限。
- 队列满时必须有明确处理策略，禁止静默丢弃打卡。
- 共享数据必须说明由哪个锁保护。
- 禁止持锁执行文件 IO、模型训练和长时间数据库操作。
- 使用多把锁时必须规定固定获取顺序。
- 线程入口必须捕获未处理异常并转换为系统错误状态。
- C++17没有 `std::jthread` 和 `std::stop_token`，停止机制必须使用项目定义的停止标志、条件变量和明确的 `requestStop()/join()` 协议。

时间使用规则：

- 超时和时间间隔使用 `std::chrono::steady_clock`。
- 业务考勤时间使用系统时间或 RTC。
- 禁止使用系统时间计算线程超时，因为管理员修改时间会造成时间跳变。

## 12. 内存和资源规范

- 文件、数据库语句、线程、锁和设备句柄必须使用 RAII。
- 禁止手工管理可以由标准对象管理的资源。
- 运行高频路径应该避免重复分配大块内存。
- 摄像头帧缓冲应该复用或使用固定容量缓冲池。
- 队列中的图像数量必须受限。
- 禁止无限增长的缓存、事件订阅和日志文件。
- `new` 和 `delete` 不能散落在业务代码中。
- 使用 `std::vector` 时应该根据预期容量调用 `reserve()`。
- 大对象应避免无意义复制，必要时使用移动语义。
- 数据库、摄像头和模型资源必须在退出前显式释放。

### 12.1 平台资源定位

- PC 配置用于完整功能开发和诊断，不以低内存为默认优化目标。
- 树莓派 Zero 2 W 配有 512MB 内存，用于真实外设原型和 ARM 平台验证，不能视为 64MB 目标设备。
- `target-lowmem` 用于约束依赖、缓冲、线程和可选功能，最终结论必须在真实目标板及其 BSP 上复测。
- 64MB 表示整机物理内存，应用预算必须扣除内核、页缓存、设备服务、共享库和显示缓冲。
- 目标板未确定前不得承诺固定的应用内存上限；必须先记录 BSP 环境，再由评审确定预算。

### 12.2 图像与队列要求

- 摄像头帧队列初始容量应限制为 2 至 4 帧，并由平台资源配置明确指定。
- 队列满时必须区分“允许丢弃的预览帧”和“禁止静默丢弃的业务事件”。
- 低内存配置应优先评估 320x240 灰度检测，显示、抓拍和识别分辨率按精度测试决定。
- 禁止在循环中无评估地使用 `cv::Mat::clone()`、`copyTo()` 和颜色空间重复转换。
- 多线程共享图像时必须明确缓冲所有权、只读阶段和可复用时机。
- 人脸注册或训练结束后必须释放样本图像和中间矩阵，禁止将完整样本永久保留在内存中。

### 12.3 资源测量要求

每次低内存优化必须记录：

```text
硬件与操作系统/BSP版本
构建配置和编译类型
输入分辨率、模型和测试数据
空闲、启动、模型加载、识别、导出阶段的RSS/PSS
峰值内存、线程数量、线程栈和动态库列表
二进制及主要依赖大小
测量命令、持续时间和重复次数
```

只报告 `free`、单次 RSS 或“运行正常”不构成资源验收。使用 cgroup 或 systemd 在 Zero 2 W 上限制内存时，报告必须标注为模拟约束，不能写成 64MB 目标板实测。

## 13. 数据库和文件规范

- SQL 只能出现在存储实现层。
- 所有外部输入必须使用参数绑定，禁止拼接 SQL。
- 多步骤业务写入必须使用事务。
- 数据库迁移必须有版本号。
- 禁止启动时无条件执行 `ALTER TABLE`。
- 图片保存应该使用“临时文件写入 + 原子重命名”。
- 数据库失败时不能提示打卡成功。
- 删除数据库记录时必须处理关联图片。
- 删除文件失败不能被静默忽略。
- 备份和恢复后必须执行完整性检查。
- 批量导入必须支持事务和回滚。
- 禁止使用可能造成隐式删除语义的 `INSERT OR REPLACE`，优先使用明确 UPSERT。

## 14. 硬件适配规范

- 业务代码不能包含 GPIO 编号、设备节点和厂商 SDK 调用。
- GPIO、摄像头、RTC、USB、指纹设备、蜂鸣器、继电器和补光灯通过HAL接口访问。
- 硬件能力接口放在 `src/hal/`，板卡实现分别放在 `src/platform/pc/`、`src/platform/raspberry_pi/` 和 `src/platform/lowmem_linux/`。
- 模拟实现不能混入真实设备实现。
- 每个硬件接口必须定义初始化失败行为、超时时间、重试策略、线程安全性、断开行为和资源释放方式。
- 硬件寄存器、协议字段和 GPIO 编号必须使用具名常量。
- 驱动实现必须注明对应硬件手册章节、协议版本或厂商 SDK 版本。
- `Application` 不能通过平台宏逐个创建设备对象；每个平台必须实现相同签名的 `PlatformFactory`。
- 每个必需HAL接口在每个构建配置中都必须有真实实现、模拟实现或可观测空实现，不能依赖未定义符号完成链接。
- 禁止使用含义模糊的单个 `device_io.cpp` 同时承载摄像头、RTC、蜂鸣器、继电器和补光灯等无关职责。
- `IStorageDevice` 负责存储容量和文件系统能力，`IUsbDevice` 负责USB连接、枚举和安全移除；两者职责不能混为一个布尔检测函数。
- `IFingerprintDevice` 负责串口或USB协议和设备错误码转换；`FingerprintEngine` 只通过该接口编排录入和识别，不直接包含串口或厂商SDK调用。

### 14.1 原型和量产边界

- Zero 2 W 是当前实体原型平台，不是最终量产 SoC 的承诺。
- 原型底板可以承载供电保护、RTC、蜂鸣器、补光灯、按键和外部接口，但业务代码不能依赖底板的具体 GPIO 编号。
- 当前阶段不设计包含 BGA 和 DDR 的完整 SoC 主板；平台迁移能力通过接口和构建配置保留。
- 从旧树莓派项目迁移代码前必须检查许可证、依赖版本、GPIO API、线程模型和错误处理，禁止直接整目录复制。
- 摄像头、显示、按键、RTC 和设备 IO 必须能够分别做独立冒烟测试，再进入整机联调。
- 生物识别模块不能自行打开摄像头或创建采集线程；摄像头HAL和采集Worker负责产生具有明确所有权的图像帧。

## 15. 日志规范

统一日志等级：

```text
TRACE：高频调试信息，正式版本默认关闭
DEBUG：开发诊断信息
INFO：启动、退出、配置加载、正常业务事件
WARN：可恢复异常或性能退化
ERROR：单次功能失败
FATAL：应用无法继续运行
```

禁止将大量散落的 `printf`、`cout` 作为正式日志方案。

正式日志必须：

- 包含时间、线程、模块和错误码。
- 支持日志滚动。
- 限制日志总容量。
- 禁止记录密码、指纹、人脸模板和完整敏感数据。
- 正式版本可以降低日志级别，但不能完全关闭错误日志。

## 16. 安全规范

- 禁止明文保存密码。
- 禁止使用 `std::hash` 保存密码。
- 默认管理员首次使用必须修改密码。
- 敏感操作必须进行权限校验。
- 清空记录、恢复出厂和导出数据必须二次确认。
- 管理操作必须写审计日志。
- U盘导入必须校验文件大小、格式和路径。
- 禁止执行由外部输入拼接的 Shell 命令。
- 升级包必须有校验值和数字签名。
- 人脸、指纹和抓拍图片应根据产品安全要求加密或限制访问。
- 密钥不能直接写在源代码或普通配置文件中。

## 17. 测试要求

每个业务模块必须具备对应测试。

### 17.1 单元测试

至少覆盖：

- 时间解析。
- 跨天班次。
- 排班优先级。
- 周末和节假日。
- 迟到、早退和旷工。
- 重复打卡。
- 应用生命周期。
- 密码验证。
- `Result<T, E>`成功、错误和`void`特化。
- Presenter状态转换且不依赖LVGL控件。
- 强类型事件订阅、退订和错误线程使用约束。
- TaskManager重复启动保护、停止和join。

### 17.2 集成测试

至少覆盖：

- SQLite CRUD。
- 数据库迁移。
- 事务回滚。
- 打卡完整链路。
- 登录认证完整链路。
- PlatformFactory对象装配完整性。
- 报表生成。
- 批量导入。
- 图片和数据库一致性。

### 17.3 设备与故障测试

至少覆盖：

- 摄像头断开和重连。
- 磁盘满。
- 文件系统只读。
- U盘拔出。
- 系统时间跳变。
- 队列满。
- 突然断电。
- 连续运行。
- 高频按键和重复页面切换。
- 页面重复进入退出后订阅数量不增长。
- 后台事件只能由UI线程消费并更新LVGL。

业务核心代码覆盖率建议不低于 80%，关键考勤规则建议达到 90% 以上。

## 18. CMake和构建规范

- 每个主要模块应该形成独立 CMake Target。
- Target 之间通过 `target_link_libraries` 表达依赖。
- 禁止通过全局命令污染头文件搜索路径和编译选项。
- 逐步取消不可控的 `GLOB_RECURSE`。
- 不允许在项目中强制写死 Debug 构建。
- 提供 Debug、Release、ASan、TSan 和设备交叉编译配置。
- 编译至少开启 `-Wall`、`-Wextra`、`-Wpedantic`。
- 新增编译警告不能被忽略。
- CI 中必须执行配置、编译、测试和静态检查。
- 测试失败不能通过 `|| true` 忽略。
- 第三方依赖必须固定版本并记录许可证。
- 所有自研Target必须继承或显式设置C++17，禁止单个Target私自提升到C++20或C++23。
- CI或构建检查必须能发现`std::expected`、`std::jthread`等超出C++17基线的使用。

### 18.1 标准构建配置

项目必须逐步提供以下可重复配置：

| 配置               | 目标              | 必须验证                               |
| ------------------ | ----------------- | -------------------------------------- |
| `simulator-full` | PC/WSL 完整仿真   | 配置、编译、单元测试、必要的 Sanitizer |
| `rpi-zero2w`     | Zero 2 W 实体原型 | 交叉编译或原生编译、部署、设备冒烟测试 |
| `target-lowmem`  | 64/128MB 产品预研 | 最小依赖构建、资源报告、裁剪功能测试   |

每种配置必须使用独立构建目录。禁止在已有构建目录中修改平台变量后继续增量编译，因为缓存依赖可能造成错误链接或错误验收。

### 18.2 工具链、平台和功能开关

- `CMAKE_TOOLCHAIN_FILE` 只负责编译器、sysroot、CPU 参数和依赖查找路径。
- `SA_PLATFORM` 只负责选择 `platform/pc`、`platform/raspberry_pi` 或 `platform/lowmem_linux` 实现。
- `SA_ENABLE_*` 只负责选择 XLSX、诊断、可选图像编解码等能力。
- 平台宏必须使用统一前缀，例如 `SA_PLATFORM_PC`，禁止继续扩散含义不清的 `RPI_BUILD`。
- CMake 应通过 `target_sources()` 只选择一个平台目录及其 `platform_factory.cpp`，不能让所有平台实现参与编译后再依赖宏隐藏大段代码。
- 可选依赖必须按功能开关查找；关闭 XLSX 时不应仍强制查找或链接 xlsxwriter。
- 交叉编译必须使用目标 sysroot 中的头文件和库，禁止链接宿主机 `/usr/lib` 或写死 `/usr/include/opencv4`。

### 18.3 条件编译边界

条件编译允许用于：

- 平台适配层引入 Linux、树莓派或厂商 SDK 头文件。
- 编译期移除目标设备不具备的可选能力。
- 隔离第三方库的版本差异。

条件编译禁止用于：

- 在 PC 和板端实现两套考勤规则。
- 在不同认证方式中复制打卡流程。
- 绕过接口直接从 UI 访问 GPIO、SQLite 或摄像头。
- 用宏隐藏未解决的线程安全、所有权和错误处理问题。

编译期开关决定能力是否进入产物；队列容量、SQLite 缓存、设备节点和超时时间原则上使用强类型运行配置。功能组合增加后，必须优先减少无意义组合，避免产生无法测试的配置矩阵。

## 19. 代码提交和评审要求

一次提交应该只解决一个明确问题。

禁止在同一提交中同时进行：

```text
大规模文件移动
+ 业务逻辑修改
+ 数据库结构修改
+ 算法替换
+ UI重做
```

代码评审必须检查：

- 模块职责是否清晰。
- 是否出现反向依赖。
- 是否增加全局状态。
- 资源是否正确释放。
- 错误是否被正确处理。
- 是否存在线程安全问题。
- 注释是否解释关键约束。
- 是否有对应测试。
- 是否修改无关文件。
- 是否提供验证结果。
- 是否使用了超出C++17基线的语言或标准库能力。
- Presenter是否持有LVGL对象、线程、Repository或平台实现。
- 事件负载、订阅生命周期和回调线程是否符合强类型事件规范。
- ApplicationServices是否演变为Service Locator。
- 每个构建平台是否仍能提供完整HAL对象集合。

## 20. 完成定义

一个任务只有同时满足以下条件才算完成：

```text
代码实现完成
+ 构建通过
+ 自动化测试通过
+ 无新增编译警告
+ 错误路径已处理
+ 资源可以正确释放
+ 文档和注释已更新
+ 不破坏PC仿真版本
+ 有明确验收方法
+ 可以安全回退
```

平台相关任务还必须满足：

- `simulator-full` 不因板端修改而失效。
- 修改的平台配置已经完成配置和编译；有硬件时完成设备冒烟测试。
- 不能执行的板端测试必须明确标记为“未验证”，不能以 PC 测试代替。
- 涉及性能或内存的结论包含修改前后数据和可重复测量方法。
- 涉及功能裁剪时，文档明确说明被移除能力、产品影响和恢复方式。
- 新增C++代码能够在项目规定的C++17工具链下编译，不依赖更高标准。
- 新增事件具备强类型负载、明确线程语义和可自动退订的句柄。
- 新增页面逻辑没有扩大UiController单例或创建新的全功能Presenter。

## 21. 规范落地要求

本规范不能只依赖开发人员人工记忆，应逐步通过工具自动检查：

- 使用 clang-format 统一代码格式。
- 使用 clang-tidy 和 cppcheck 进行静态检查。
- 使用 CTest 执行自动化测试。
- 使用 ASan、UBSan、TSan 检查内存、未定义行为和线程竞争。
- 使用 CI 执行构建、测试和质量门禁。
- 使用代码评审模板检查模块边界、注释、测试和回滚方案。

规范调整必须经过评审。由于硬件 SDK 或性能约束需要例外时，应记录适用模块、原因、风险和替代措施，不能以临时绕过方式长期保留。

## 22. Codex与AI辅助开发规范

### 22.1 配置职责

- 根目录 `AGENTS.md` 保存仓库长期有效规则，包括架构边界、禁止事项、构建测试命令、资源约束和评审要求。
- 项目 Codex 配置只保存仓库需要的工具、沙箱或执行默认值，不复制工程规范正文。
- Skill 保存重复使用的专项流程和检查脚本，不用于堆放整个项目背景。
- 详细设计和业务知识必须保存在仓库文档中，不能只存在对话、个人提示词或个人 Skill 中。

第一批项目 Skill 建议为：

| Skill                        | 适用任务                     | 核心检查                                           |
| ---------------------------- | ---------------------------- | -------------------------------------------------- |
| `smartattendance-refactor` | 生命周期、模块拆分、依赖反转 | 影响面、模块边界、测试、回退点                     |
| `smartattendance-lowmem`   | 资源审计和依赖裁剪           | ELF、动态库、RSS/PSS、线程、队列、图像复制、SQLite |

树莓派移植进入实施阶段后再创建 `smartattendance-board-porting`。只有当发布检查流程经过实际项目验证并稳定重复后，才创建 `embedded-release-check`。

### 22.2 AI生成代码的责任边界

- AI 生成代码必须执行与人工代码完全相同的编译、测试、静态检查和评审要求。
- AI生成或建议的C++代码必须先检查C++17兼容性，禁止根据更新标准的常见写法引入`std::expected`、`std::jthread`等能力。
- 开始修改前必须阅读相关实现、调用方、测试、构建配置和本规范，禁止仅根据文件名推测结构。
- 一个任务只完成一个可验收目标；未经明确授权，不扩大为全目录重写、算法替换或数据库迁移。
- 不得覆盖无法确认来源的工作区改动，不得通过恢复文件来获得“干净差异”。
- 不能声称未实际执行的构建、测试、板端运行或性能数据已经通过。
- AI 给出的架构建议必须结合当前代码、目标硬件和资源数据验证，不能以通用最佳实践代替项目证据。
- 开发者必须能够解释合入代码的依赖方向、生命周期、错误路径、测试方法和关键取舍。

### 22.3 Codex单次任务流程

```text
读取约束和相关代码
    ↓
确认任务边界、风险和验收方式
    ↓
实施一个最小可验证改动
    ↓
运行与风险匹配的构建和测试
    ↓
检查差异、资源影响和文档一致性
    ↓
报告结果、未验证项和下一步
```

涉及重构时，输出必须包含行为是否变化；涉及硬件时，必须区分编译验证、模拟验证和实板验证；涉及优化时，必须包含基线、测量条件和对比结果。

## 23. 学习与项目复盘要求

本项目同时用于嵌入式工程能力训练和秋招展示，因此每个重要改动必须沉淀以下内容：

1. 原实现存在的具体问题和触发条件。
2. 采用的企业工程原则及其在本项目中的落地方式。
3. 被放弃方案、当前方案和选择理由。
4. 自动化测试、实板测试或测量证据。
5. 修改前后的行为、资源或可靠性变化。
6. 尚未解决的风险和下一阶段验证方法。

最终项目材料至少包含架构图、模块依赖图、线程模型、三套构建说明、硬件接口表、关键测试报告、资源对比报告、稳定性报告、整机演示和重要设计决策记录。简历和面试描述必须使用可复现数据，不得把计划中的能力写成已经完成的结果。
