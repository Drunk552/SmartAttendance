# SmartAttendance 嵌入式项目重构目录方案

## 1. 文档目的

本文档用于规划 SmartAttendance 智能离线人脸考勤终端的软件目录重构方案。

本项目属于嵌入式终端软件，不按照 Web 前后端项目进行拆分。重构重点是明确应用生命周期、核心业务、设备接口、平台实现、数据存储、图形界面和算法模块之间的边界，同时保留现有的 LVGL、OpenCV、SQLite、SDL2 仿真和目标硬件适配能力。

### 当前技术栈基线

当前重构阶段只锁定公共代码和 PC 仿真必须稳定的技术栈：C++17、C11、CMake 最低 3.16、LVGL 9.4.0，以及 `simulator-full`、`rpi-zero2w`、`target-lowmem` 三种构建配置。LVGL 版本以仓库内 `libs/lvgl/lv_version.h` 为准。

OpenCV、摄像头管线、SQLite/Freetype/SDL2 的精确版本和目标板工具链暂不在本阶段冻结。它们必须在硬件确定、交叉编译和资源测试完成后，按版本、来源、许可证、编译选项和校验值形成独立版本清单。当前 PC 依赖版本不得直接视为量产板基线。

本文档描述的是目标结构，不要求一次性移动全部代码。实际实施应采用渐进式重构，每完成一个小阶段都必须保持项目能够编译、运行和回退。

## 2. 重构原则

1. 保持嵌入式模块化单体架构，不引入不必要的网络服务或微服务。
2. PC/WSL 仿真版本和真实设备版本共用同一套核心业务代码。
3. 核心考勤规则不能依赖 LVGL、SQLite、OpenCV、SDL 或具体硬件 SDK。
4. UI 不直接操作 SQLite，也不直接实现考勤业务规则。
5. 人脸、指纹、卡片和密码认证最终统一进入同一个打卡服务。
6. 具体硬件实现放在平台适配层，通过抽象接口供上层调用。
7. 长期运行线程必须具备明确的启动、停止和资源回收流程。
8. 每次只迁移一个职责明确的模块，避免大范围同时改名和移动。
9. PC、树莓派 Zero 2 W 和后续低内存设备共用核心业务代码，只替换平台实现和可选能力。
10. 条件编译只能用于平台选择、第三方依赖隔离和功能裁剪，不能复制或分叉考勤业务规则。
11. Zero 2 W 用于实体原型和外设联调，64/128MB 目标用于约束架构和资源预算，两者不能视为相同运行环境。
12. 所有性能与资源优化必须先建立基线，再以可重复的数据证明效果。

### 2.1 C++语言基线

项目所有自研 C++ 代码统一使用 C++17，不允许为了局部便利引入 C++20 或 C++23 语法和标准库类型。

- 允许使用 `std::optional`、`std::variant`、`std::filesystem`、`std::string_view` 等 C++17 能力。
- 禁止使用 `std::expected`、`std::jthread`、`std::stop_token`、`std::span`、`std::format` 和 Ranges。
- 文档中的 `Result<T, E>` 表示项目自定义的 `smart_attendance::Result`，不是 `std::expected`。
- 交叉编译工具链必须完整支持项目实际使用的 C++17 标准库能力。

## 4. 各模块职责

### 4.1 `app`：整机应用生命周期

`app` 负责整个终端的初始化、启动、运行和退出顺序，不实现具体考勤规则。

主要职责：

- 初始化日志和配置。
- 初始化数据库。
- 初始化设备和算法模块。
- 启动后台工作线程。
- 启动 LVGL UI。
- 接收退出信号。
- 按正确顺序停止线程并释放资源。

`Application`、`ApplicationServices` 和 `TaskManager` 的职责必须分开：

| 类型                    | 唯一职责                                                    | 禁止事项                                     |
| ----------------------- | ----------------------------------------------------------- | -------------------------------------------- |
| `Application`         | 作为唯一组合根，控制整机初始化、运行和退出顺序              | 不计算考勤规则，不提供全局Service查询        |
| `ApplicationServices` | 通过显式成员持有Repository、业务Service、算法和基础设施对象 | 不创建线程，不实现泛型`get<T>()`服务定位器 |
| `TaskManager`         | 持有Worker、队列和线程，执行`start/requestStop/join`      | 不创建Repository和Service，不操作LVGL页面    |

建议生命周期顺序：

```text
加载配置和日志
    ↓
PlatformFactory创建当前平台HAL对象
    ↓
ApplicationServices创建数据库、Repository、算法和Service
    ↓
TaskManager启动后台Worker
    ↓
UI初始化并进入主循环
    ↓
停止接收新的UI和设备输入
    ↓
TaskManager请求停止并join全部线程
    ↓
ApplicationServices逆序释放业务和存储资源
```

建议最终将 `main.cpp` 简化为：

```cpp
int main() {
    Application app;
    const auto initResult = app.initialize();
    if (!initResult) {
        return 1;
    }
    return app.run();
}
```

### 4.2 `core`：核心业务规则

`core` 只保存纯业务模型和规则，不允许直接包含下列依赖：

- LVGL
- SQLite
- OpenCV
- SDL2
- GStreamer
- GPIO
- 具体硬件厂商 SDK

该层应能在没有摄像头、屏幕和数据库的环境中单独编译并执行单元测试。

`core/common/result.h` 提供项目自定义的 `Result<T, E>`。普通版本可以基于 C++17 `std::variant<T, E>` 实现，`Result<void, E>` 必须提供明确特化。`Result` 用于表达可预期失败；“没有查询到数据”优先使用 `std::optional`；不能失败的纯函数直接返回值。

### 4.3 `services`：业务流程编排

`services` 将多个底层模块组合为一个完整终端功能。例如 `PunchService` 负责：

```text
接收认证结果
    ↓
读取用户信息和当天排班
    ↓
执行重复打卡检查
    ↓
调用考勤规则计算状态
    ↓
保存考勤记录和抓拍图片
    ↓
向UI返回标准化结果
```

人脸、指纹、密码和卡片认证成功后，都应调用同一个 `PunchService`，不能各自实现一套考勤逻辑。

认证职责固定拆分为：

- `PasswordPolicy` 和 `PermissionRule` 位于 `core/auth`，只实现纯规则。
- `IPasswordHasher` 位于 `core/auth/password_hasher.h`，只定义抽象，不依赖具体密码库。
- `AuthenticationService` 位于 `services`，负责查询用户、调用哈希验证、更新失败状态和生成认证结果。
- `Pbkdf2PasswordHasher` 位于 `infrastructure/security`，负责具体安全哈希实现。

### 4.4 `biometric`：生物识别算法

该模块只负责生物特征的检测、注册、识别和模型管理，不直接打开摄像头、不拥有采集线程，也不直接写考勤记录。摄像头采集属于 HAL 实现和采集 Worker，算法模块只接收具有明确所有权的 `ImageFrame`。

建议提供统一接口：

```cpp
class IBiometricEngine {
public:
    virtual ~IBiometricEngine() = default;
    virtual Result<IdentifyResult, BiometricError> identify(
        const ImageFrame& frame) = 0;
    virtual Result<EnrollResult, BiometricError> enroll(
        int userId, const ImageFrame& frame) = 0;
    virtual Result<void, BiometricError> remove(int userId) = 0;
};
```

PC 仿真版本可以继续使用 OpenCV LBPH；真实设备版本可以通过相同接口接入厂商人脸或指纹 SDK。

### 4.5 `storage`：数据和文件存储

`storage` 负责 SQLite、图片文件、备份和数据库迁移。

建议将当前较大的 `db_storage.cpp` 按数据类型拆分为多个 Repository。`storage/repository` 只保存不暴露 SQLite 类型的抽象接口，`storage/sqlite` 保存具名的 `Sqlite*Repository` 具体实现。上层业务只通过 Repository 接口读写数据，不直接使用 SQL。

### 4.6 `ui`：LVGL界面

UI 层负责：

- 页面创建和销毁。
- 焦点和按键导航。
- 显示业务状态。
- 收集用户输入。
- 调用 Presenter 并根据Presenter状态刷新控件。

UI 层不负责：

- 直接执行 SQL。
- 计算迟到、早退和旷工。
- 直接管理摄像头线程。
- 保存密码和生物特征。

本项目不采用依赖数据绑定框架的完整 MVVM，而采用适合 LVGL C 回调模型的轻量 Presenter：

- Presenter 持有页面需要的 UI 无关状态，例如加载状态、选中项、查询条件、分页信息和错误提示。
- Presenter 通过构造函数持有 Service 的非拥有引用，不直接依赖 Repository、SQLite、OpenCV 和 HAL 实现。
- Presenter 接收页面命令、调用 Service，并将结果转换为页面可显示状态。
- Presenter 不持有 `lv_obj_t*`，不创建或销毁控件，不管理线程，不作为单例。
- Presenter 默认由页面或 UI 管理器创建，并在对应页面销毁前释放。
- 后台结果通过有界 UI 事件队列送达 UI 线程，再由 Presenter 更新状态并触发页面刷新。

现有 `UiController` 不允许整体迁移为某个 Presenter。其业务编排迁入 Service，数据库访问迁入 Repository，摄像头缓存迁入采集 Worker，线程迁入 `TaskManager`，页面状态才进入各 Presenter。

### 4.7 `hal`：硬件抽象接口

该目录只定义设备能力，不包含某一块具体板卡的实现。

建议至少抽象以下接口：

```text
ICamera
IDisplay
IKeypad
IRtc
IStorageDevice
IUsbDevice
IFingerprintDevice
IBuzzer
IRelay
IIllumination
IWatchdog
IPowerManager
```

### 4.8 `platform`：平台接口实现

`platform/pc` 保存 PC/WSL 仿真实现，例如 SDL 显示、SDL 键盘、GStreamer 摄像头和可观测的无硬件输出实现。

`platform/raspberry_pi` 保存 Zero 2 W 原型实现，例如 V4L2 摄像头、Framebuffer/DRM 显示、GPIO 矩阵键盘、RTC、蜂鸣器和补光灯。

`platform/lowmem_linux` 保存后续 64/128MB 目标设备实现。目标 SoC 尚未确定前，只定义接口、资源约束和可编译桩实现，不提前绑定厂商 SDK。

上层代码只依赖 `hal` 中的接口，不直接判断当前是 WSL、树莓派或目标 MPU。每个平台必须提供相同签名的 `platform_factory.cpp`，由 CMake 只选择其中一个参与构建，确保 `Application` 中不出现平台条件编译。

平台工厂返回显式拥有HAL对象的 `PlatformDevices`，对象所有权随后交给 `ApplicationServices`：

```cpp
struct PlatformDevices {
    std::unique_ptr<ICamera> camera;
    std::unique_ptr<IDisplay> display;
    std::unique_ptr<IKeypad> keypad;
    std::unique_ptr<IRtc> rtc;
    std::unique_ptr<IWatchdog> watchdog;
};

Result<PlatformDevices, PlatformInitError> createPlatformDevices(
    const DeviceConfig& config);
```

实际结构体需要包含本产品启用的全部必需HAL接口。工厂不能启动长期线程，设备初始化失败必须返回具体错误，禁止用空指针表示未解释的失败。

### 4.9 `infrastructure`：通用基础设施

用于放置不属于具体业务的公共能力：

- 日志。
- 强类型事件总线。
- 有界任务队列。
- 后台 Worker。
- 系统健康监控。
- 统一错误码。

强类型事件采用“事件结构体即负载”的设计，不使用 `EventType + void*`：

```cpp
struct TimeUpdated {
    std::string displayText;
};

struct DiskStateChanged {
    bool isFull;
    std::uint64_t freeBytes;
};
```

事件总线对外提供 C++17 模板接口：

```cpp
template <typename Event>
SubscriptionHandle subscribe(std::function<void(const Event&)> handler);

template <typename Event>
void publish(const Event& event);
```

不额外定义通用 `Event<T>` 包装层。需要跨线程进入 UI 的有限事件集合使用 `std::variant` 存入有界队列，例如 `using UiEvent = std::variant<TimeUpdated, DiskStateChanged, RecognitionCompleted>`。

事件模型必须满足：

- `SubscriptionHandle` 只能移动，析构时自动退订。
- EventBus 通过依赖注入使用，禁止继续作为全局单例。
- 同步发布的回调运行在发布线程；非 UI 线程回调禁止调用 LVGL。
- 后台线程通过有界 `UiEvent` 队列通知 UI，由 UI 线程消费。
- 事件不能携带裸指针、局部变量地址和生命周期不明确的引用。
- 摄像头帧不通过 EventBus 复制，只发布状态、帧序号或固定缓冲索引。
- 需要返回结果的查询和命令继续使用普通函数调用，不经过事件总线。

## 5. 模块依赖关系

推荐依赖方向：

```text
UI
 ↓
Services
 ↓
Core

Presenters ──→ Services
Services   ──→ Core、Biometric抽象接口、Repository抽象接口、HAL接口
Storage    ──→ 实现Repository抽象接口
Platform   ──→ 实现HAL接口
App        ──→ 负责装配接口与具体实现
```

必须避免以下反向依赖：

```text
Core        → LVGL
Core        → SQLite
Core        → OpenCV
Storage     → UI页面
Biometric   → UI页面
UI          → SQLite SQL语句
HAL接口     → 具体平台实现
Presenter   → LVGL控件对象
```

培训项目要求的三层架构与细分目录对应关系如下：

| 培训要求 | 本方案对应模块                                    |
| -------- | ------------------------------------------------- |
| UI层     | `ui/screens`、`ui/common`、`ui/presenters`  |
| 业务层   | `core`、`services`、`biometric`、`report` |
| 数据层   | `storage`                                       |

`app`、`hal`、`platform` 和 `infrastructure` 是嵌入式终端必须具备的装配与横切支撑层，不改变项目仍是单进程模块化单体的性质。

## 8. 每个阶段的安全要求

每次重构提交应满足：

1. 只处理一个明确模块。
2. 不同时进行大规模文件移动和业务逻辑修改。
3. 修改前后都能完成 CMake 配置和编译。
4. 核心业务修改必须有对应测试。
5. 不删除旧接口，先通过适配层过渡。
6. 新接口稳定后再删除旧实现。
7. 数据库结构变更必须提供迁移和回滚方案。
8. 保留可运行的 PC/WSL 仿真版本。

推荐使用以下提交粒度：

```text
提交1：增加Application骨架，不改变行为
提交2：数据库初始化交由Application管理
提交3：增加线程停止和join流程
提交4：增加PunchService及测试
提交5：人脸识别改为调用PunchService
提交6：拆分EmployeeRepository
```

不要使用如下方式进行一次性重构：

```text
同时移动全部源码
+ 修改数据库结构
+ 修改考勤规则
+ 更换人脸算法
+ 重写CMake
+ 重做全部UI页面
```

这种方式出现问题后很难判断故障来自哪一层，也很难快速回退。

## 10. 目标平台与构建矩阵

本项目长期维护一套源码和三类构建配置。构建配置选择参与编译的平台实现、第三方依赖和可选功能，不允许改变核心考勤语义。

| 构建配置           | 运行环境              | 用途                         | 默认依赖与能力                                        |
| ------------------ | --------------------- | ---------------------------- | ----------------------------------------------------- |
| `simulator-full` | x86_64 PC/WSL         | 日常开发、调试和自动化测试   | SDL2、完整 OpenCV、Freetype、xlsxwriter、诊断工具     |
| `rpi-zero2w`     | ARM Linux、Zero 2 W   | 实体原型、外设联调和现场演示 | V4L2、Framebuffer/DRM、GPIO、RTC、必要的 OpenCV 模块  |
| `target-lowmem`  | 64/128MB 嵌入式 Linux | 低成本产品预研和资源门禁     | 最小 LVGL、最小 OpenCV 或替代算法、固定缓冲、按需导出 |

`CMAKE_TOOLCHAIN_FILE` 负责选择编译器、sysroot、CPU 参数和查找路径；`SA_PLATFORM` 负责选择平台源文件；`SA_ENABLE_*` 只负责裁剪可选能力。三者不得混为一个 `RPI_BUILD` 宏长期使用。

建议配置方式：

```cmake
set(SA_PLATFORM "pc" CACHE STRING "Target platform")
set_property(CACHE SA_PLATFORM PROPERTY STRINGS pc rpi_zero2w lowmem_linux)

option(SA_ENABLE_XLSX "Enable XLSX export" ON)
option(SA_ENABLE_DIAGNOSTICS "Enable development diagnostics" ON)
```

每个配置必须使用独立构建目录，不允许在同一构建目录中切换平台：

```text
build/simulator-full/
build/rpi-zero2w/
build/target-lowmem/
```

## 11. 条件编译与配置边界

推荐采用“统一接口 + 分平台源文件 + CMake 选择实现”的方式。条件编译只允许出现在以下位置：

- CMake 平台和功能选择。
- `config/feature_config.h` 中由 CMake 生成或校验的功能宏。
- `platform/*` 内隔离 Linux 头文件、厂商 SDK 和设备 API。
- 第三方库适配代码。

禁止在 `core`、考勤规则和统一打卡流程中编写两套业务逻辑：

```cpp
// 禁止：PC和板端执行了不同的考勤规则。
#if SA_PLATFORM_PC
calculateAttendanceForPc();
#else
calculateAttendanceForDevice();
#endif
```

编译期开关决定“能力是否进入产物”，运行时配置决定“资源使用量和设备参数”。摄像头缓冲数量、队列容量、SQLite 缓存和超时时间应通过强类型配置对象管理，不能散落为宏和魔法数字。

## 12. 硬件原型与产品平台路线

当前硬件路线确定为：

```text
PC完整功能基线
    ↓
树莓派 Zero 2 W 实体原型
    ↓
自制功能底板 + 外设 + 3D打印外壳
    ↓
低内存构建和资源验证
    ↓
按需要迁移到最终低成本SoC
```

Zero 2 W 配有 512MB 内存，用于尽快跑通摄像头、显示、按键、RTC、蜂鸣器、补光灯、USB 导出和开机自启动。它不等价于真实产品可能采用的 64MB 平台，不能以“树莓派可以运行”替代低内存验收。

原型阶段将 Zero 2 W 作为可更换主板，自制底板承载供电保护、RTC、蜂鸣器、补光灯、按键和外部接口。当前不设计包含 BGA、DDR 的完整 SoC 主板。外壳建模不属于软件主线，但软件团队必须提供屏幕开孔、摄像头视场、PCB 安装孔、接口位置、排线空间和散热边界。

## 13. 低内存资源约束

64MB 是整机约束，不是应用进程可以独占的内存。最终预算必须在目标 BSP、内核和设备服务确定后重新测量。目标板未确定前，先执行以下强制约束：

- 记录空闲、启动、摄像头打开、模型加载、识别和导出阶段的 RSS/PSS 峰值。
- 摄像头队列必须有界，初始目标为 2 至 4 帧，禁止保存无上限完整 BGR 帧。
- 检测优先评估 320x240 灰度图，显示、抓拍和识别按实际精度需求选择分辨率。
- 避免高频 `cv::Mat::clone()` 和隐式深拷贝，优先复用固定缓冲。
- SQLite 缓存必须按平台配置；现有约 20MB 缓存不能直接进入低内存配置。
- 重新评估 `temp_store=MEMORY`，训练或注册完成后及时释放样本和临时图像。
- 板端关闭 LVGL examples/demos、未使用字体、解码器和控件。
- OpenCV 初始评估仅保留 `core`、`imgproc`、`objdetect`、`face`，其他模块以依赖分析结果为准。
- 统计线程数量和线程栈预算，禁止用新增线程绕过模块设计问题。
- 所有资源指标必须记录测量环境、输入数据、命令、平均值和峰值，保证可复现。

可以在 Zero 2 W 上使用 cgroup 或 systemd 做应用内存限制和 OOM 路径测试，但该结果只能作为预研数据，不能代替真实 64/128MB 板卡的整机验证。

## 14. Codex 辅助开发配置

Codex 配置分为三层，各自职责不能混用：

1. 根目录 `AGENTS.md`：保存本仓库长期有效的模块边界、禁止事项、构建命令、测试门禁、低内存约束和代码评审要求。
2. 项目 `.codex/config.toml`：只保存可信仓库内需要的沙箱、工具或模型默认设置，不承载工程规范正文。
3. Skill：保存可重复执行的专项工作流、检查脚本和按需加载的参考资料。

第一批只建立两个项目 Skill：

| Skill                        | 触发场景                         | 必须输出                                                 |
| ---------------------------- | -------------------------------- | -------------------------------------------------------- |
| `smartattendance-refactor` | 实施模块迁移、解耦或生命周期重构 | 影响范围、依赖变化、最小补丁、测试结果、回退点           |
| `smartattendance-lowmem`   | 检查或优化板端资源               | 动态库、ELF、RSS/PSS、线程、队列、图像复制和 SQLite 报告 |

树莓派移植开始后再增加 `smartattendance-board-porting`；稳定发布流程形成后再增加 `embedded-release-check`。Skill 中不复制本仓库的详细规范，而是引用本文件和《嵌入式工程化开发规范》。重复执行且要求确定性的测量过程应实现为脚本。

个人使用的 Skill 默认安装到 `~/.codex/skills/<skill-name>/`。其中只保存触发条件和执行流程；工程规范、硬件约束、测量脚本及结果仍应保存在本仓库，确保项目不依赖某台开发机的个人配置才能理解和验收。

Codex 每次实现任务都必须遵循：阅读相关代码和约束、陈述影响面、完成单一小步修改、运行匹配风险的测试、检查差异、报告未验证项。AI 生成代码与人工代码执行完全相同的评审和验收标准。

## 15. 总体实施路线与阶段门禁

| 阶段              | 主要交付物                                   | 完成门禁                                   |
| ----------------- | -------------------------------------------- | ------------------------------------------ |
| 0. 工程基线       | 构建说明、问题清单、资源基线、`AGENTS.md`  | 当前PC功能可重复构建和验证                 |
| 1. 应用生命周期   | `Application` 接管真实启动、停止和线程回收 | 无重复初始化、无残留线程、生命周期测试通过 |
| 2. 核心业务       | 领域模型、`PunchService`、Repository接口   | 核心考勤规则脱离UI/数据库可测试            |
| 3. 多平台构建     | 三套Preset、工具链、平台接口和实现选择       | PC、Zero 2 W、低内存配置均能配置或冒烟编译 |
| 4. 树莓派原型     | 摄像头、显示、输入、RTC、设备IO和自启动      | 离线考勤闭环可演示，连续运行24小时         |
| 5. 低内存优化     | 依赖裁剪、固定缓冲、资源对比报告             | 功能测试通过且指标满足经评审的预算         |
| 6. 产品可靠性     | 故障注入、数据库恢复、日志轮转、看门狗       | 24/72小时稳定性和关键故障测试通过          |
| 7. 整机与求职材料 | 功能底板、整机演示、架构和性能报告           | 能解释设计取舍、验证方法和量化结果         |

当前已经形成阶段二的最小统一生命周期结构。`Application` 作为组合根控制初始化、运行和退出顺序；`ApplicationServices` 通过显式成员持有旧数据库与业务模块的生命周期适配器，不创建线程，也不提供通用服务查询；`TaskManager` 不再初始化业务资源，只管理有界队列、Worker、停止请求和 `join()`。UI 初始化和关闭通过显式 `UiLifecycle` 管理，主线程循环由 `Application::run()` 驱动；停止时先等待全部 Worker，再释放 LVGL/SDL、业务资源和数据库。时间与磁盘状态通过容量固定为一个最新快照的 `UiSystemStatusMailbox` 交给 UI 主线程消费，主页在磁盘空间不足时显示告警图标。记录查询和考勤统计页面的个人/全员报表以及员工设置表导入导出已迁入容量为 4 的有界 UI 后台任务队列。主页生命周期使用同步调用，人脸录入预览由页面自有 LVGL 定时器刷新固定帧缓冲，遗留的全局 `EventType + void*` EventBus 已删除。运行文件统一写入可执行文件同级的 `runtime/` 目录，页面中已无分离线程或永久事件订阅。阶段三已新增不依赖 UI、SQLite 和 OpenCV 的 `PunchService`、打卡领域规则及最小 Repository 抽象，通过 Fake Repository 验证排班、重复打卡、状态计算和写入失败链路；现有 `db_storage` 已通过过渡 Repository 适配器接入并使用临时 SQLite 数据库验证时间戳写入、JPEG 抓拍和重复打卡。`ApplicationServices` 通过具名成员持有三个过渡 Repository 和唯一 `PunchService` 实例，且不会隐式打开数据库。实际运行的人脸识别成功路径已改为向容量 10、单张抓拍上限 512 KiB 的队列投递拥有所有权的请求，由打卡 Worker 调用统一服务；采集 Worker 不再直接查询或写入考勤数据库。`business_get_frame()` 无条件返回后的不可达旧识别与重复打卡实现、规则缓存以及无调用方的 `AttendanceRule::recordAttendance()` 直接写库入口已经删除，旧 `AttendanceRule` 只保留报表和 UI 尚在使用的纯规则兼容接口，不再依赖 OpenCV 或 SQLite。其中宽容时间解析已迁入 `core` 并通过兼容测试固定现有格式，旧 `timeStringToMinutes()` 仅映射无效输入的 `-1` 返回值。当前代码没有密码、卡片或指纹的运行时打卡入口：密码仅用于员工管理和管理权限验证，指纹功能尚未开发；因此本阶段没有可迁移的这三类入口。算法和 HAL 对象尚未装配。

阶段三完成结论：`PunchService` 已将各 Repository 的显式错误和异常都收敛为具体打卡错误，旧 `main.cpp` 中会绕过服务直接写考勤的未调用演示代码已删除。按当前仓库已存在的人脸打卡入口，阶段三代码范围已完成；密码、卡片、指纹入口及真实摄像头整机验证按当前迭代明确后置，其中真实人脸打卡链路仍标记为未验证。算法和 HAL 对象的拆分装配属于后续人脸模块和平台抽象阶段。

班次归属的间隔中点与跨天判定已收敛到 `core::determineShiftOwner()`，`PunchService` 和旧报表兼容接口共用同一纯规则；旧接口只保留本地时间戳及 `1/2` 返回值适配。
正常、迟到、旷工、早退及跨天的单班段状态计算已收敛到 `core::calculatePunchStatus()`，旧 `AttendanceRule::calculatePunchStatus()` 只保留本地时间戳和旧枚举适配。
报表中的打卡状态优先级已收敛到 `core::isPunchStatusBetter()`，旧整数状态接口仅保留状态码与历史哨兵值兼容。
阶段四完成结论：原 `src/data/db_storage.cpp` 已拆除，数据库连接、Schema 初始化、播种和关闭迁入 `src/storage/database.*`，其余 SQL 按组织、员工、考勤、排班、配置与维护职责迁入 `src/storage/sqlite/`。`storage/repository/` 已分别提供员工、考勤、排班和配置抽象；`ApplicationServices` 继续使用具名成员装配具体过渡 Repository，没有引入 Service Locator。`src/data/db_storage.h` 仅作为旧 UI 和报表调用方的兼容入口，旧函数签名、数据库表、运行目录和数据格式保持不变，后续迁移调用方时可以逐个删除兼容 API，不需要再次移动 SQL。

2026-08-06 软件架构收敛补充：主程序 CMake 源文件已改为显式清单；生产代码控制台输出统一经过带等级、时间、线程、模块、操作和错误码字段的日志边界，并支持有限容量文件轮转。旧 DAO 兼容 DTO 已迁至命名空间化的 `core/model/legacy_database_models.h`，`db_storage.h` 只保留旧函数声明和 SQLite 适配别名，业务和 UI 不再包含该头文件。`UiManager` 由 `Application` 唯一持有并通过页面专用依赖显式注入，不再使用函数静态单例。PC 构建新增 `simulator-full` Preset；目标板工具链和硬件配置仍按既定范围后置。

员工只读链路新增不含密码和生物特征的 `core::Employee`、`IEmployeeRepository`、`EmployeeService` 和轻量 `EmployeeLookupPresenter`；按 ID 查询与单页最多 64 条的分页查询均明确区分参数错误、未找到和读取失败。配置 Repository 同样区分配置/节假日不存在与 SQLite 读取失败。临时 SQLite 集成测试覆盖员工查找与分页、配置和节假日 CRUD、表损坏、数据库关闭、考勤时间戳写入、JPEG 抓拍和重复打卡。阶段四没有修改 Schema，也没有迁移员工写操作或重做 UI；这些旧调用方继续通过兼容头工作，Presenter 拆分仍属于阶段七。

## 16. 最终目标

重构完成后，项目应达到以下状态：

- `main.cpp` 只负责启动应用。
- 数据库全程只有一个受控生命周期。
- 所有后台线程都可以安全停止并回收。
- 所有认证方式共用统一打卡服务。
- 核心考勤规则可以脱离 UI 和硬件独立测试。
- PC、Zero 2 W 和低内存设备只在 `platform` 实现、资源配置和明确裁剪的可选能力上存在差异。
- UI 页面不直接操作数据库和硬件。
- OpenCV 或厂商算法可以通过统一接口替换。
- 数据库、模型、配置和软件版本都能够独立管理和升级。
- 每一个重构阶段都有可编译、可测试、可回退的版本。
- 三套构建配置具有独立、可重复的构建和验收记录。
- 树莓派原型能够完成真实外设上的离线考勤闭环。
- 低内存结论由测量数据支撑，并清楚区分模拟限制与目标板实测。
- 项目能够沉淀架构、测试、性能和硬件联调材料，用于复盘和面试说明。
